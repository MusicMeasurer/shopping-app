# Проверки SQL · ShoppingApp

## Уровни доказательств

1. **Static**: `python3 -m unittest discover -s tests/sql -p 'test_*.py' -v`. Без PostgreSQL. Проверяет только текст и наличие защитных конструкций.
2. **Schema/ACL**: после установки 001–016 и REVIEW_ONLY патча в **одноразовой** базе запустить `cloud/drafts/SECURITY_PREFLIGHT_READ_ONLY.sql` через psql с `ON_ERROR_STOP=1`. Ноль строк нарушений — только предварительный результат.
3. **Behavioral**: отдельные тесты с настоящими пользователями A/B, JWT, PostgREST, негативными запросами и RPC. **Ещё не автоматизированы**.
4. **Concurrency**: параллельные транзакции, повторы операций, передача владения и приглашения 017. **Ещё не автоматизированы**.

## Запреты
- Не направлять команды на действующий TEST `tdcrtwpewbngoermckmx` и на production.
- Не хранить ключи, пароли, service_role/JWT в GitHub или логах.
- Не запускать 017: миграция REVIEW_ONLY, схема не испытана.
- Черновик ACL с номером 018 не является разрешением на применение; порядок миграций требует согласования.

## Известные ограничения
- GitHub workflow пока запускает только Static, а не настоящую базу.
- Проверки `information_schema.role_table_grants` не покрывают все унаследованные/PUBLIC привилегии; для этого в preflight также используется `has_table_privilege` и `has_function_privilege`.
- Результат `0 rows` не подтверждает корректность RLS-предикатов или безопасность SECURITY DEFINER.
- Не считать тесты пройденными без ссылки на фактический прогон и его результат.
