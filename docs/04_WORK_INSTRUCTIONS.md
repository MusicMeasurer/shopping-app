# 04 · Рабочие инструкции ShoppingApp

**Редакция:** 2026-11-27 (1.7). **Статус:** согласованный справочник рабочих процедур.

## Общие правила

- Актуальный источник инструкций — `main/docs/04_WORK_INSTRUCTIONS.md`. Перед выполнением команды прочитать соответствующую инструкцию в GitHub, не полагаться на память или PDF.
- В начале задачи открой [«С чего начать работу над ShoppingApp»](START_HERE.md) из `main`. Это точка входа для нового чата и рабочей сессии. Если доступен только режим чтения GitHub, укажи, какие действия можно подтвердить в нём.
- Инструкции применяются к повторяющимся операциям. Указание номера запускает процедуру для названной задачи; отсутствие номера не отменяет обязательных принципов разработки.
- Значимые решения, результаты испытаний и изменения состояния фиксируются в документации по мере работы, а не только по отдельному вызову инструкции 2.
- Различать согласованное решение, предложение, реализованный код и проверенное поведение. При конфликте источников — установить и показать расхождение, не подменять решение собственным.
- Не изменять `main`, production, рабочие данные и платные ресурсы без соответствующего разрешения; содержательные изменения документации разрешены только в `main/docs/` по согласованному поручению.

## Инструкция 1 · Разработка и автоматическая проверка

**Цель:** реализовать согласованную задачу и подтвердить работоспособность результата.

1. Открой `main/docs/START_HERE.md` и проверь указанные там репозиторий, рабочую ветку и контрольный коммит. Убедись, что рабочая ветка включает последнюю согласованную основу и что она подходит для задачи. Перед первой правкой сообщи рабочую ветку и исходный коммит. Если основа недоступна или расходится с согласованной, останови правки и покажи конкретное расхождение. Затем прочитай актуальные принципы, требования, архитектуру и относящиеся к задаче решения.
2. Определи ожидаемый результат, затронутые функции, риски и критерии приёмки.
3. Реализуй изменение в рабочей ветке, используя существующие решения и избегая дублирования.
4. Создай или обнови необходимые модульные, интеграционные, регрессионные и негативные тесты.
5. Запусти проверки. При ошибках найди причину, исправь и повтори необходимые проверки до получения результата.
6. Проверь взаимодействие нового кода с существующим функционалом.
7. Зафиксируй изменения в GitHub и сообщи: коммит, результаты проверок, ограничения и прямую ссылку на GitHub Actions.
   Для проверок с тестовой БД сверь итог задания и конкретного шага на точном SHA через список запусков нужного workflow; зачёт предыдущего SHA допускается исключительно по правилу эквивалентности hosted ниже. Для push проверяй события push, поскольку выборка только по pull request такие запуски пропускает. В отчёте отдельно укажи результат локального прогона и результат прогона с тестовой БД.

**Правила:** не выдавай успешную сборку за полноценную приёмку; не изменяй production и main без разрешения; не закрывай задачу, если её критерии не выполнены. При блокировке сообщи точную причину, не имитируя завершение. При выявлении ошибки, требующей изменения согласованного функционала, останови задачу и сообщи о проблеме и предлагаемых способах её решения.

**Граница:** результаты автоматических проверок являются исходными данными для инструкции 4 и не заменяют пользовательскую приёмку.

**Критерии тестирования SDK (согласовано 27.11.2026).** Проверять требуемый наблюдаемый результат операции и состояние данных/защитных барьеров, а не количество внутренних действий SDK или HTTP-запросов. Точное количество запросов проверять только когда оно является согласованным критерием безопасности, производительности, идемпотентности либо необходимо для подтверждения конкретного тестового предусловия. Не подменять проверку результата ожиданием счётчика; сохранять негативные проверки и различать локальный результат и серверный отзыв.

### Экономия времени автоматических испытаний (24.11.2026)

1. До правок определить минимально достаточный набор проверок по рискам и зависимостям задачи, отличая целевые испытания от общей регрессии. На промежуточных коммитах выполнять модульные проверки, сборку и необходимые целевые интеграционные/браузерные проверки; полный комплект hosted-испытаний запускать на итоговом коммите задачи либо зачесть предыдущий успешный прогон по правилу эквивалентности hosted ниже. Исключение — обоснованная необходимость полной регрессии раньше, например при изменениях безопасности или общего контракта данных; причину фиксировать.
2. Не ставить в очередь полные hosted-прогоны каждого промежуточного SHA. Перед очередным запуском сверять существующие workflow и их HEAD; при необходимости безопасно отменять устаревшие ещё не начатые запуски, если доступно управление. Не прерывать операции с тестовой БД без подтверждения безопасного завершения/очистки. Если автоматические триггеры создают лишние прогоны, скорректировать CI отдельной проверяемой технической задачей, сохранив обязательный итоговый контроль и сериализацию доступа к общей лаборатории. Не отключать проверки ради получения зелёного статуса.
3. Длинные комплексные сценарии разделять на независимые воспроизводимые испытания, где это не разрушает проверяемую сквозную последовательность. Использовать изолированные тестовые данные и очистку, не допускать конкурентных изменений общих тестовых аккаунтов. Браузерные проверки приложения сохранять в iPhone WebKit.
4. Устанавливать разумные ограниченные тайм-ауты отдельных интерфейсных действий и ожиданий по характеру операции, не оставлять обычное открытие меню/диалога ждать общего многоминутного тайм-аута сценария. При сбое сохранять точное действие, состояние интерфейса и доступную диагностику. Ожидание появления и доступности любой кнопки и её нажатия — не более 10 секунд (согласовано 24.11.2026). Ограничение задавать явно в общей конфигурации и не превышать в отдельных тестах. Ожидание серверной операции выделять в самостоятельную проверку фактического состояния, не маскируя его ожиданием кнопки. Согласованные максимумы: обычные меню/диалоги — 10 s; локальное сохранение — 5 s; авторизация — 15 s; подтверждение серверной записи — 15 s; получение изменений с другого устройства — 20 s; начальная облачная синхронизация — 30 s. Разделять ожидания фаз, не складывать повторные попытки ради обхода лимита. Общий лимит сквозного сценария и лимит задания CI задаются отдельно; виртуальное время модульных тестов не ограничивает реальное ожидание. Исключения требуют отдельного согласования, диагностику сохранять.
5. После исправления повторять необходимый набор проверок, включая затронутые зависимости; на финальном SHA подтверждать обязательный полный комплект hosted и критерии задачи. Оптимизация не уменьшает покрытие, не ослабляет утверждения тестов, не заменяет проверку безопасности или пользовательскую приёмку. В отчёте различать ожидание очереди, фактическое выполнение и тайм-аут; не считать успех предыдущего SHA доказательством готовности нового без доказанной эквивалентности по следующему правилу.

**Правило эквивалентности hosted (согласовано 27.11.2026).** Если после успешного полного hosted-прогона изменены исключительно тесты, которые не выполняются и не используются hosted-проверками, допускается зачесть этот прогон для финального SHA без повторного запуска. Перед зачётом: (1) сверить полные Git tree обоих коммитов и точный diff; (2) подтвердить неизменность продуктового кода, схемы/миграций, сборки, зависимостей, конфигурации, hosted workflow, тестов, скриптов, фикстур и общих вспомогательных модулей; по фактическим командам и зависимостям hosted подтвердить, что изменённый тест не входит в его область; (3) подтвердить завершение всех обязательных jobs/steps предыдущего hosted на его точном SHA и успешные обязательные проверки финального SHA, включая изменённый тест; (4) убедиться в отсутствии известных изменений целевой тестовой среды или иных предусловий, влияющих на достоверность результата; (5) записать оба SHA, ссылки на прогоны, diff и обоснование в журнал. В отчёте явно различать зачтённый hosted и фактический запуск на финальном SHA. При любом изменении hosted-зависимостей, значимом изменении среды, неполной проверке или сомнении — новый полный hosted на финальном SHA обязателен. Правило не отменяет негативные проверки, физическую приёмку и требования безопасности.

### Режим автономного выполнения

1. Команда «Инструкция 1» означает полный цикл разработки по текущей согласованной задаче, а не одно произвольно выбранное промежуточное действие.
2. Не останавливайся после коммита, запуска тестов или промежуточного результата. Продолжай до выполнения критериев приёмки в пределах автоматических проверок либо до объективной блокировки.
3. Если автоматическая проверка ещё выполняется, дождись её окончательного результата. При ошибке установи причину, исправь и повтори необходимые проверки.
4. Не заменяй основную задачу вспомогательной без доказанной необходимости. После необходимой вспомогательной работы возвращайся к основной.
5. Промежуточные сообщения не считаются завершением работы и не должны прерывать выполнение процедуры.
6. Итоговый отчёт предоставляй после завершения полного цикла либо при объективной блокировке. Указывай выполненные критерии, доказательства, ограничения и оставшиеся действия.
7. Не называй ожидание CI, объём работы или ограничение времени технической блокировкой, если доступно безопасное продолжение. Если продолжение действительно невозможно, точно укажи причину.

**Контроль перед завершением:** «Если я сейчас закончу ответ, будет ли задача выполнена в соответствии с Инструкцией 1? Если нет — существует ли объективная причина, по которой я не могу продолжать?»

**Уточнение границы:** «полный цикл» здесь означает реализацию и автоматическую проверку в рамках инструкции 1; пользовательская приёмка и выпуск выполняются отдельно по инструкциям 4 и 5.


## Инструкция 2 · Документация и аудит решений

**Цель:** привести документацию в соответствие с фактическим состоянием проекта и принятыми решениями.

1. Прочитай актуальные документы проекта из `main/docs/`.
   **Контроль целостности больших документов (27.11.2026):** если размер файла в Git tree приближается к 1 MiB или Contents API вернул пустое/неполное содержимое, читать фактический Git blob по SHA, а не считать пустой ответ содержимым файла. Перед правкой сверять SHA, размер, начало и конец; для дописывания проверять сохранение всего исходного текста. После создания нового blob проверять полное содержимое до перемещения ref, затем сверять новый HEAD и blob. При неполном чтении или неожиданном сокращении остановить запись и восстановить историю из Git, не перезаписывать или сбрасывать чужие коммиты.
2. Изучи изменения GitHub и доступную историю обсуждений после последней актуализации.
3. Выдели выполненные работы, результаты проверок, ошибки, принятые решения и открытые вопросы.
4. Актуализируй `05_DEV_LOG.md`, включая ссылки на подтверждающие коммиты и проверки. При смене рабочей ветки, публикации, приёмке или согласовании следующего шага обнови краткое состояние в `START_HERE.md`.
5. Проверь необходимость изменений в принципах, требованиях, архитектуре и дорожной карте.
6. Исправь устаревшие фактические сведения и противоречия, не изменяя согласованных решений.
7. Представь краткий отчёт: что обновлено, что осталось открытым, какие решения требуют согласования.

**Правила:** не придумывай отсутствующую историю; отличай подтверждённые решения от предложений; при противоречии между источниками не выбирай новый вариант самостоятельно. Содержательные изменения основных документов выполняй только в `main/docs/`.

## Инструкция 3 · Проверка соответствия

**Цель:** установить, соответствует ли реализация ранее согласованным требованиям и решениям.

1. Прочитай актуальные требования, архитектуру, дорожную карту и связанные записи журнала.
2. Найди относящиеся к проверяемой функции решения в доступной истории обсуждений.
3. Сопоставь согласованное поведение с фактическим кодом и результатами испытаний.
4. Определи утраченные функции, временные упрощения, противоречия, неподтверждённые возможности и риски.
5. Раздели отклонения на критические, существенные и не препятствующие продолжению работы.
6. Представь перечень расхождений с источниками, последствиями и предлагаемыми исправлениями.

**Правила:** не трактуй отсутствие записи как согласие; не заменяй исходное требование более удобным техническим решением; не изменяй код или продуктовые решения без соответствующего поручения.

## Инструкция 4 · Пользовательская приёмка

**Цель:** подтвердить работоспособность реализованной функции в реальных пользовательских условиях.

1. Изучи результаты автоматических проверок и критерии приёмки.
2. Определи, какие пользовательские сценарии ещё не подтверждены и требуют дополнительных испытаний.
3. Проведи самостоятельно все доступные испытания, не повторяя без необходимости уже подтверждённые проверки. Если поручение включает выкладку на полигон, перед ней сверяй и называй исходный коммит, адрес и базу. После выкладки проверь опубликованный адрес и фактическую ревизию.
4. Если необходима ручная проверка на стороне пользователя, подготовь минимальный набор конкретных действий.
5. Зафиксируй фактические результаты, обнаруженные дефекты и непроверенные сценарии.
6. Представь заключение о соответствии функции критериям приёмки.

**Правила:** выкладка на полигон по согласованному поручению не является разрешением на боевую публикацию (инструкция 5); не считать успешный CI доказательством прохождения пользовательской приёмки; не повторять уже подтверждённые испытания без причины; не объявлять непроверенные сценарии проверенными.

## Инструкция 5 · Подготовка выпуска

**Цель:** подготовить проверенное изменение к выпуску без риска для рабочей версии.

1. Проверь состав изменений, зависимости, состояние CI, регрессионные испытания и известные ограничения.
2. Убедись, что документация отражает фактическую готовность функций.
3. Проверь миграции данных, безопасность, возможность восстановления и план отката.
4. При необходимости проведи независимый аудит безопасности, архитектуры и совместимости.
5. Составь заключение о готовности к выпуску и перечисли блокирующие замечания. Для публикации укажи исходный коммит, адрес и целевую базу.
6. Запроси отдельное разрешение на слияние в main, изменение production или публикацию.
7. После разрешения выполни согласованные действия и проверь опубликованный адрес и фактическую ревизию. Боевой GitHub Pages публикуется только явным ручным запуском workflow `Deploy ShoppingApp to GitHub Pages` (`workflow_dispatch`, ветка `main`) после сверки согласованного HEAD; commit/push/merge в `main`, включая обновление `docs/`, не является запуском или разрешением публикации. Сохранить обязательные проверки сборки и приёмочные барьеры; если ручной запуск недоступен исполнителю, указать это, не заменять его автоматическим push. Автоматические проверки рабочей ветки и отдельная процедура полигона остаются действующими.

**Правила:** подготовка не равна публикации; не выполнять необратимые операции и не расходовать платные ресурсы без согласования; не объявлять выпуск успешным до проверки опубликованной версии.
