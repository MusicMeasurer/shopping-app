## Вывод по причине повторных «новых уязвимостей»

**Подтверждено:** несколько событий, воспринимавшихся как новые проблемы, были ошибками тестовой инфраструктуры, расширением покрытия, предупреждениями конфигурации или недостатком доказательств. **Не подтверждено:** что каждое повторное замечание — новая эксплуатируемая уязвимость миграции. Также нельзя доказать, что предыдущие проверки исчерпывали весь риск.

**Корневая процессная причина (аналитический вывод):** отсутствовали зафиксированная заранее матрица покрытия, единый реестр с дедупликацией, базовая линия предупреждений конкретной среды и разделение SQL CI / hosted migration / Auth HTTP / production readiness. Из-за этого новая проверка выглядела как новый дефект.

## Постоянный контроль для следующей миграции

1. До работы: версия SQL и схема, затрагиваемые роли/данные, угрозы, матрица проверок и критерии готовности.
2. До применения: снимок полей, ограничений, грантов, RLS, контрольных данных и advisor baseline.
3. CI: чистая установка, upgrade с данными, негативные сценарии, конкуренция, регрессии прежних RPC; каждый найденный дефект — тест.
4. После: сравнение снимков и advisor delta; классификация по A-ID вместо создания дубликатов.
5. Отчёт: доказательства (ссылки на run/commit), что не проверено, открытые риски, отдельно статус production.
6. HTTP/JWT, UX и выпуск — отдельные ворота, не подменяющие и не отменяющие SQL-аудит.
