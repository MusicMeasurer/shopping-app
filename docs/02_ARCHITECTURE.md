# 02 · Архитектура данных и ресурсов

**Редакция:** 2026-11-04 · целевая архитектура, без дублирования журнала испытаний.
**Назначение:** утверждённые принципы, текущая реализация, кандидаты и технические риски.  
**Важно:** не путать **реализовано**, **согласовано** и **гипотеза**.


## 1. Слои системы

```text
Siri / Apple Shortcuts ──> защищённый API [ПЛАН]
                                 │
ShoppingApp PWA ──> слой операций с данными ──> IndexedDB [РАБОТАЕТ]
                                 │
                                 └──> адаптер синхронизации ──> облачный сервис [ПЛАН]
                                                        │
                                           аккаунты, списки, права [ПЛАН]
```

- **Реализовано:** React + TypeScript + Vite PWA; GitHub Pages; локальное IndexedDB, базовые операции со списками, офлайн-доступ.
- **Согласовано:** offline-first; локальные личные списки без входа; после авторизации — облако, резервное хранение и совместные списки; разделение бизнес-логики и поставщика данных.
- **Не реализовано:** авторизация, облачная база, серверный API, синхронизация, общий доступ, обработка голосовой команды в целевом списке.

## 2. Модель данных

| Сущность | Локально | В облаке после входа | Примечание |
|---|---|---|---|
| Списки и позиции | Да, IndexedDB | Да, для синхронизируемых списков | Сейчас реализованы позиции с `id`, `listId`, `name`, `purchased`, `createdAt`; расширение модели требует миграции |
| Количество, единица, тип списка | План | План | Не вводить произвольные значения по догадке |
| Архив и версии завершения | План | План | Отдельные записи; не терять историю |
| Пользователь, участники и права | Не требуется для гостя | Да | Серверная проверка доступа обязательна |
| Очередь офлайн-операций | План | Синхронизируется | Повторная отправка не должна создавать дубли |
| Секреты и привилегированные ключи | **Нет** | Только защищённая серверная сторона | Никогда не в PWA или Shortcut |

**Границы хранения:** данные Safari и установленной iOS PWA могут находиться в разных изолированных хранилищах. Открытие URL из «Команд» в Safari не доказывает запись в базу установленной PWA. При отсутствии облака нельзя обещать единый список между ними.

## 3. Ресурсы и зависимости

| Ресурс | Статус | Назначение / ограничение |
|---|---|---|
| `MusicMeasurer/shopping-app` (GitHub) | Используется | Репозиторий кода, история, GitHub Actions; права записи помощников **не подтверждены** |
| GitHub Pages | Работает | Публикация `https://musicmeasurer.github.io/shopping-app/` |
| GitHub Actions | Работает | Сборка и деплой при push в `main`; проверять результат каждого выпуска |
| IndexedDB (`idb`) | Работает | Данные на устройстве; очистка данных браузера может их удалить |
| Apple Shortcuts / Siri | Частично испытано | Диктовка и запись файла при блокировке; URL открывается в Safari, в том числе при блокировке; полноценная запись товара не испытана |
| Codex | Временно недоступен | Разработка; ранее возникали ошибки доступа/сети; не считать возможность push гарантированной |
| Working Copy | Временный обходной путь | На iPhone push проверен; пробный Pro 10 дней, дальнейший бесплатный сценарий не подтверждён |
| Supabase | **Выбран для лабораторного прототипа; клиентская интеграция не готова** | PostgreSQL, авторизация, права, синхронизация; условия/лимиты проверить непосредственно перед подключением |
| Firebase / иной backend | Альтернатива | Потребуется адаптер и план миграции; прямой взаимозаменяемости API нет |
| Переводчик / API | Не выбран | Отдельное решение по качеству, офлайн и стоимости |

## 4. Обязательные принципы безопасности
- HTTPS/TLS при передаче; шифрование при хранении у провайдера проверяется отдельно. Это **не** означает сквозное шифрование.
- Авторизация для синхронизации и общих списков; вход не нужен для локальных личных списков.
- Права доступа проверяются на сервере / уровне базы (например, RLS при выборе Supabase), не только в интерфейсе.
- Siri отправляет запрос от имени конкретного авторизованного пользователя; **никаких service-role/admin ключей в Shortcut, клиенте или URL**.
- Предусмотреть ограничение злоупотреблений, безопасное хранение/отзыв токенов, идемпотентность запросов, обработку сетевых ошибок.
- Перед публичным запуском: проверка доступа между аккаунтами, политики удаления и экспорта данных, резервного восстановления и условий обработки персональных данных.

## 5. Синхронизация: решения до реализации
- Отдельный адаптер между UI и хранилищем; сохранение существующего локального поведения.
- Явные идентификаторы операций/объектов для защиты от дублей при повторах Siri и сетевых ретраях.
- Определить источник истины для синхронизируемых списков, стратегию конфликтов, порядок удаления и восстановления, границу локальных/общих данных.
- Определить миграцию гостевых списков при входе и выходе из аккаунта; исключить незаметную потерю данных.
- Сравнить стоимость не только по мегабайтам, но и по операциям, трафику, авторизации, активности и доступности.

## 7. Приглашения в общие списки — согласованная модель

- Владелец создаёт ограниченную по сроку одноразовую ссылку.
- Ссылку принимает **первый авторизованный пользователь, который ещё не является участником списка**; привязки к получателю нет.
- Владелец и существующие участники не могут принять ссылку; повторное использование и отзыв должны блокировать вступление.
- При передаче владения незавершённые приглашения отзываются атомарно.
- SQL 017 проверен в изолированной среде, но **пользовательская функция не выпущена**. Подтверждения и оставшиеся выпускные ограничения — в `05_DEV_LOG.md` и `07_MIGRATION_017_RELEASE_GATE.md`.

## 8. E2 → E3: граница готовности (2026-11-04)

**Подтверждено:** в изолированной `shoppingapp-migration-lab` существуют таблицы `shopping_lists`, `shopping_items`, `item_operations` и функции `apply_item_change`, `pull_item_changes`, `can_access_list`. Это проверка наличия схемы и сигнатур, **не** проверка готовности пользовательской интеграции. Предыдущие HTTP A/B и RPC испытания зафиксированы в журнале с их ограничениями. Миграция 017 относится к E8 и не является условием E3.

**Минимальные решения, которые нужно принять до реализации E3:**
1. **Авторизация:** определить способ входа в PWA и отдельный безопасный способ передачи пользовательского полномочия из Apple Shortcuts, в том числе при блокировке. Запрещены service-role/admin ключи в клиенте. Конкретный механизм пока **не утверждён**; проверка на настоящем iPhone — критерий E3, а не повод заранее считать его работающим.
2. **Граница данных:** гостевые списки остаются в IndexedDB; для синхронизируемых списков после входа нужен явный источник истины и правила привязки локальных списков к облачным UUID. Не переносить, не заменять и не удалять гостевые данные молча. Поведение при первом входе, выходе и конфликте пока **открыто**.
3. **Воспроизводимая база:** зафиксировать проверенную последовательность базовых миграций 001–016 и нормализации ACL; проверить на одноразовом стенде без ручных исправлений. Применённую лабораторную 017 не изменять задним числом. Отдельная готовность к рабочему выпуску и реальные пользовательские сценарии относятся к E3/E7.
4. **Стоимость:** до подключения внешнего облака проверить действующие бесплатные лимиты и возможные платные зависимости; ничего платного без отдельного разрешения.

**Критерий закрытия E2:** перечисленные архитектурные решения согласованы; базовая схема воспроизводима с безопасными правами; ограничения и стоимость задокументированы. Реальная авторизация, синхронизация и Siri принимаются в E3. Новые аудиты 017 не входят в этот критерий.

### E2 · Принято: вход в аккаунт (2026-11-05)
- Основной способ входа в PWA — **email + пароль через Supabase Auth**; локальные гостевые списки работают без регистрации.
- После входа пользовательская сессия сохраняется и штатно обновляется в пределах возможностей и политики Supabase Auth; бессрочная авторизация не гарантируется.
- Восстановление пароля обязательно для пользовательского пути E3.
- Siri должна действовать от имени того же пользователя без ввода пароля на каждую покупку; конкретный безопасный механизм и работа на заблокированном iPhone **ещё открыты**, проверяются на E3. Никаких привилегированных ключей в клиенте/Shortcut.
- Решение согласовано пользователем. Лабораторные учётные записи не означают готовую интеграцию авторизации в PWA.

### E2 · Принято: offline-first и семантика выхода (2026-11-05)
- Локальная IndexedDB-копия является рабочей: ранее доступные списки остаются видимыми и редактируемыми при отсутствии сети, истечении сессии и **ручном выходе**. Выход отключает синхронизацию, **не удаляет** локальные списки; интерфейс должен ясно объяснять это, в том числе риск данных на общем устройстве.
- При первом входе гостевые списки автоматически, без дополнительного подтверждения, подготавливаются к переносу в облако; защита от дублей и повторов обязательна. При отсутствии сети локальная работа продолжается. Успешная облачная запись не отменяет локальную офлайн-копию.
- После повторного входа в тот же аккаунт синхронизация возобновляется. Локальные операции передаются поштучно и идемпотентно, облачные изменения загружаются; **никакой безусловной замены всего списка**. Несинхронизированные изменения не теряются при выходе.
- При входе в **другой** аккаунт нельзя автоматически передавать туда списки и операции предыдущего аккаунта. Для E3 автоматическое переключение аккаунтов на одном устройстве не поддерживается; необходим явный безопасный сценарий смены аккаунта.
- Разрешение одновременных конфликтующих изменений одного товара пока открыто; проверка версий и отсутствие тихой потери данных — обязательные ограничения для следующего решения E2.
- Решение согласовано пользователем. Не считать поведение реализованным до E3.

### E2 · Принято: обработка конфликтов (2026-11-05)
- Операции над разными товарами объединяются независимо; изменение разных свойств одного товара можно объединять **только при доказанной безопасности** (например, переименование и отметка покупки).
- Конкурирующие изменения одного свойства, а также удаление против редактирования — конфликты. Проверять версии, не перезаписывать и не удалять незаметно ни одну сторону; хранить необходимые данные для последующего разрешения.
- Офлайн-редактирование не блокируется; при восстановлении связи конфликты выявляются и предлагаются к разрешению. На E3 сначала реализовать обнаружение/сохранность, затем минимальный пользовательский выбор; сложный интерфейс не обязателен.
- Идентификаторы операций и идемпотентность обязательны при сетевых повторах. Текущая SQL/RPC схема может потребовать доработки для слияния по полям и сохранения конфликтных версий: **это проектное решение, а не утверждение, что механизм уже реализован**.
- Согласовано пользователем 2026-11-05.

### E2 · Проверено: бесплатный план и ограничения (2026-11-05)
- Коннектор Supabase подтвердил: организация `ShoppingApp Lab` (`yivbdnnixbbuzbktkxko`) — `free`, `tier_free`; активны два лабораторных проекта. **Новых проектов не создавать без отдельного решения**: по документации Supabase на Free допускаются два бесплатных активных проекта суммарно по организациям владельца/администратора.
- Текущая документация Supabase «About billing on Supabase» (https://supabase.com/docs/guides/platform/billing-on-supabase): Free включает 500 MB базы на проект, 50 000 MAU, 5 GB egress, 1 GB Storage, 500 000 вызовов Edge Functions, 2 млн сообщений Realtime и 200 пиковых соединений. Квоты некоторых ресурсов общие на организацию; проверять актуальность перед выпуском и не трактовать лимиты как гарантию SLA/доступности.
- Supabase security advisors на `shoppingapp-migration-lab`: четыре служебные таблицы с RLS без policies (предположительно намеренный deny-by-default; подтвердить сценариями RPC), предупреждение `auth_leaked_password_protection`. По https://supabase.com/docs/guides/auth/password-security проверка утёкших паролей доступна **только Pro+**; не обещать её включение на Free. Для E3 использовать достаточную длину/сложность пароля и штатные меры Auth, без платного апгрейда.
- По read-only ACL запросу `anon` не имеет SELECT на 8 public-таблиц; `authenticated` имеет SELECT на четыре пользовательские таблицы, INSERT на shopping_lists, без прямого UPDATE/DELETE. Это **не** полноценная проверка RPC и JWT.
- Риск: бесплатные проекты могут приостанавливаться; локальные списки обязаны работать без облака. Перед реальной регистрацией пользователей нужны политика резервирования/восстановления, проверка SMTP/лимитов Auth и решение, какой проект станет пользовательским; лаборатории не считать production.
- Результат: стоимость и бесплатные границы предварительно документированы; выпуск и переход на платный тариф не согласованы. Технический gate по воспроизводимому ACL и hosted HTTP остаётся открытым.
