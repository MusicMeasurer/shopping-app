**Исполнимость цепочки `001 → 005`**

Безусловной синтаксической ошибки или очевидной ошибки разрешения имён, препятствующей первому применению всей цепочки на чистой современной Supabase, по тексту не обнаружено.

В частности:

- `revision`, `kind`, `snapshot` в запросе `005` квалифицированы через `c`, поэтому конфликта с выходными переменными `RETURNS TABLE` здесь не видно.
- Вызовы встроенных `md5`, `jsonb_build_array`, `jsonb_build_object`, `now` совместимы с пустым `search_path`: `pg_catalog` доступен неявно.
- Триггер запрета изменения владельца из `002` не запрещает изменение только `revision` в `004`.
- Политика `002`, запрещающая клиентское изменение `deleted_at`, не мешает RPC **при условии**, что владелец `SECURITY DEFINER` действительно обходит соответствующий RLS.
- `003` закрывает клиентские записи товаров, а не удаляет политики. Это допустимо: разрешающая RLS-политика сама по себе не возвращает отозванное SQL-право.

Однако успешное применение и работоспособность RPC зависят от окружения:

| Предпосылка | Что необходимо проверить |
|---|---|
| Supabase Auth | Наличие `auth.users`, `auth.uid()`, ролей `anon`, `authenticated` |
| Роль миграций | Права создавать расширение, таблицы, функции, политики и триггеры; доступ к `auth.users` |
| Владельцы объектов | RPC и функции авторизации должны принадлежать доверенным ролям с необходимыми правами и корректным обходом RLS |
| Клиентские права | Скрипты не выдают полный набор прав для создания и чтения списков; предполагаются внешние/default grants |
| Первое применение | Скрипты не предназначены для повторного запуска поверх себя: повторные `CREATE TABLE`, `ADD COLUMN`, `CREATE TRIGGER` завершатся ошибками |

Ожидаемые при нарушении предпосылок ошибки — например, `42501 insufficient_privilege`, отсутствие роли или схемы. Это **условные ошибки окружения**, а не установленная ошибка чистой Supabase.

Применять промежуточные стадии к базе, доступной клиентам, нельзя: защита всей цепочки появляется постепенно.

**H-01. Удаление владельца уничтожает общие списки вопреки утверждённым правилам**

**Тип:** дефект по коду относительно утверждённого поведения; workflow отсутствует.

**Место:** [`001_initial_schema.sql:7`](https://github.com/MusicMeasurer/shopping-app/blob/6eb6d2ce99e5b5b767d9392fd9e96c717028a09d/cloud/drafts/001_initial_schema.sql#L7), строки 15, 24; [`003_sync_tables.sql:10,17`](https://github.com/MusicMeasurer/shopping-app/blob/6eb6d2ce99e5b5b767d9392fd9e96c717028a09d/cloud/drafts/003_sync_tables.sql#L10). Требование: [`OWNERSHIP_TRANSFER_RULES.md:15–30`](https://github.com/MusicMeasurer/shopping-app/blob/6eb6d2ce99e5b5b767d9392fd9e96c717028a09d/cloud/drafts/OWNERSHIP_TRANSFER_RULES.md#L15).

**Сценарий:** A владеет списком, B является участником. Администратор или будущий backend удаляет A из `auth.users`. FK `owner_id ON DELETE CASCADE` удаляет список, затем товары, членство и журнал изменений. RLS клиентских ролей не предотвращает каскад.

**Последствия:** безвозвратная потеря общего списка вместо передачи B. Одновременно исчезает история, необходимая другим устройствам для согласования удаления.

**Ожидается:** общий список передаётся текущему участнику с минимальным `joined_at`, при равенстве — минимальным `user_id`. Личный список удаляется. Передачи, уведомления и удаление аккаунта выполняются согласованно.

**Минимальное безопасное исправление:** до реализации workflow блокировать удаление пользователя, пока существуют принадлежащие ему списки, например ограничивающим FK. Затем реализовать утверждённую транзакционную процедуру. Простого удаления запретительного триггера владельца недостаточно.

**H-02. Блокировка мутации не согласована с удалением участника**

**Тип:** дефект конкурентного протокола по коду; воспроизведение требуется.

**Место:** [`004_apply_item_change.sql:25–30`](https://github.com/MusicMeasurer/shopping-app/blob/6eb6d2ce99e5b5b767d9392fd9e96c717028a09d/cloud/drafts/004_apply_item_change.sql#L25), [`002_security_hardening.sql:42–45`](https://github.com/MusicMeasurer/shopping-app/blob/6eb6d2ce99e5b5b767d9392fd9e96c717028a09d/cloud/drafts/002_security_hardening.sql#L42). Требование: [`SYNC_PROTOCOL_V02.md:29`](https://github.com/MusicMeasurer/shopping-app/blob/6eb6d2ce99e5b5b767d9392fd9e96c717028a09d/cloud/drafts/SYNC_PROTOCOL_V02.md#L29).

`apply_item_change` блокирует строку списка через `FOR UPDATE`. Прямой `DELETE` из `list_members` такой блокировки не требует.

**Сценарий:**

1. B начинает транзакцию, успешно выполняет RPC, но ещё не делает `COMMIT`.
2. A удаляет B из `list_members` и фиксирует транзакцию.
3. B фиксирует изменение товара после завершённого удаления членства.

**Последствия:** отсутствует обещанная общая точка сериализации мутаций и отзыва членства. Возникает окно, в котором отзыв уже зафиксирован, а ранее авторизованная запись фиксируется позднее.

**Ожидается:** удаление участника и мутация используют один порядок блокировок. Либо мутация завершается перед отзывом, либо запрос после отзыва отклоняется.

**Минимальное безопасное исправление:** закрыть прямой клиентский `DELETE list_members`; выполнять выход и удаление участника через проверенную операцию, которая сначала блокирует строку списка, затем проверяет права и меняет членство. Тот же порядок обязателен для приглашений, передач владельца и удаления аккаунта.

Следует также зафиксировать поддерживаемый уровень изоляции: старые снимки длительных `REPEATABLE READ`-транзакций требуют отдельного анализа.

**H-03. Pull проверяет доступ отдельно от чтения данных**

**Тип:** дефект согласованности авторизации по коду; конкретное конкурентное воспроизведение не выполнялось.

**Место:** [`005_pull_item_changes.sql:9–21`](https://github.com/MusicMeasurer/shopping-app/blob/6eb6d2ce99e5b5b767d9392fd9e96c717028a09d/cloud/drafts/005_pull_item_changes.sql#L9).

**Причина:** проверка `can_access_list` и чтение `list_changes` — отдельные SQL-операции внутри функции. Функция по умолчанию `VOLATILE`; при `READ COMMITTED` они могут использовать разные снимки. Сам запрос журнала повторно доступ не проверяет, а выполняющий его definer обходит RLS.

**Сценарий:** проверка допускает B; затем членство B удаляется и фиксируется; после этого выполняется чтение журнала. Оно может использовать более новый снимок и вернуть события, появившиеся после отзыва.

**Последствия:** результат не соответствует единому снимку «права плюс данные». Это отличается от нормального завершения чтения уже существовавших данных по снимку до отзыва.

**Ожидается:** проверка прав и возвращаемые данные относятся к согласованному состоянию.

**Минимальное безопасное исправление:** объединить проверку и чтение в один SQL-запрос с одним снимком. Если требуется строгая сериализация с отзывом, дополнительно использовать совместимый протокол блокировок списка для pull и всех изменений членства. Определить допустимое поведение уже выполняющихся запросов.

**Medium**

**M-01. Контракт SQL-привилегий и владельцев объектов остаётся неполным**

**Тип:** непроверенный риск окружения и пробел миграций.

**Место:** [`003_sync_tables.sql:25–32`](https://github.com/MusicMeasurer/shopping-app/blob/6eb6d2ce99e5b5b767d9392fd9e96c717028a09d/cloud/drafts/003_sync_tables.sql#L25), [`002_security_hardening.sql:7–8`](https://github.com/MusicMeasurer/shopping-app/blob/6eb6d2ce99e5b5b767d9392fd9e96c717028a09d/cloud/drafts/002_security_hardening.sql#L7), [`004_apply_item_change.sql:9,84–89`](https://github.com/MusicMeasurer/shopping-app/blob/6eb6d2ce99e5b5b767d9392fd9e96c717028a09d/cloud/drafts/004_apply_item_change.sql#L84).

**Проблемы:**

- `TRUNCATE` отозван у четырёх таблиц, но **не у `list_members`**. RLS не ограничивает `TRUNCATE`.
- Нет полного определения schema/default/column privileges и наследования ролей.
- Владельцы функций явно не закреплены.
- Отзыв табличного права не отзывает отдельно выданные column grants.
- У функций авторизации `001` отозван `PUBLIC EXECUTE`, но возможные прямые default grants роли `anon` отдельно не отозваны.
- Триггерные функции сохраняют стандартные права исполнения, если окружение не меняет их.

**Последствия:** при широких внешних grants возможны лишние полномочия; при узких — RPC или легитимные клиентские действия не работают. Неверный владелец RPC может получить отказ RLS при мягком удалении; неверная модель владельцев функций авторизации — рекурсивное применение политик.

**Ожидается:** миграции создают воспроизводимую модель доступа.

**Минимальное безопасное исправление:** явно определить доверенных владельцев, разрешённые действия каждой роли, права схемы и функций; закрыть `TRUNCATE list_members`; проверить column grants, наследование и default privileges.

Сам по себе пропуск `TRUNCATE` **не доказывает эксплуатацию через обычный PostgREST CRUD**: нужен доступный путь выполнения этой команды. Наличие такого пути здесь не установлено.

`service_role` следует считать доверенной административной ролью: она может обходить RLS и писать напрямую при наличии прав. При этом она не отменяет обычные триггеры. Её использование не заменяет протокол синхронизации.

**M-02. Клиент может задать начальную серверную ревизию списка**

**Тип:** дефект ограничений по коду при наличии необходимого клиенту `INSERT`.

**Место:** [`003_sync_tables.sql:4,32`](https://github.com/MusicMeasurer/shopping-app/blob/6eb6d2ce99e5b5b767d9392fd9e96c717028a09d/cloud/drafts/003_sync_tables.sql#L4), [`001_initial_schema.sql:77–78`](https://github.com/MusicMeasurer/shopping-app/blob/6eb6d2ce99e5b5b767d9392fd9e96c717028a09d/cloud/drafts/001_initial_schema.sql#L77).

`003` оставляет создание списков клиентом. Проверка вставки требует правильного владельца и отсутствия удаления, но не `revision = 0`.

**Сценарий:** A вставляет свой список с `revision = 9223372036854775807`. Первый вызов мутации пытается выполнить `revision + 1` и завершается переполнением `bigint`.

**Последствия:** созданный список нельзя изменять через RPC. Можно также задать произвольную ненулевую начальную ревизию без соответствующей истории.

**Ожидается:** серверный курсор начинается с определённого значения и не управляется клиентом.

**Минимальное безопасное исправление:** отдельная операция создания списка либо ограниченные права вставки и проверка начальной ревизии. Аналогично определить серверные значения времён списка. Общий `CHECK (revision = 0)` на таблице непригоден: он запретит последующие ревизии.

**M-03. Отсутствует завершённый контракт начального снимка, retention и исчезновения списка**

**Тип:** пробел дизайна; частично прямо отмечен авторами.

**Место:** [`005_pull_item_changes.sql:16–26`](https://github.com/MusicMeasurer/shopping-app/blob/6eb6d2ce99e5b5b767d9392fd9e96c717028a09d/cloud/drafts/005_pull_item_changes.sql#L16), [`003_sync_tables.sql:4–24`](https://github.com/MusicMeasurer/shopping-app/blob/6eb6d2ce99e5b5b767d9392fd9e96c717028a09d/cloud/drafts/003_sync_tables.sql#L4), [`004_apply_item_change.sql:72–76`](https://github.com/MusicMeasurer/shopping-app/blob/6eb6d2ce99e5b5b767d9392fd9e96c717028a09d/cloud/drafts/004_apply_item_change.sql#L72).

**Сценарии:**

- Товар существует до применения `003`; ему назначается версия, но событие в журнал не добавляется. Pull с нулевого курсора его не восстановит.
- Будущая очистка журнала оставит клиента со старым курсором, но механизма `cursor too old` нет.
- После удаления списка или отзыва доступа клиент получает общее исключение `List unavailable`. Не определено, как он прекращает повторы и обрабатывает локальную копию.
- Снимок события не включает `created_at` и другие поля полной серверной записи. Использовать его как полноценный снимок товара без дополнительного контракта нельзя.

**Последствия:** неполное восстановление состояния, потенциальные пропуски после будущей очистки, бесконечные повторы недоступных операций.

**Ожидается:** полный снимок с согласованной ревизией, понятное восстановление после устаревания курсора и обработка потери доступа.

**Минимальное безопасное исправление:** определить API снимка и его границу, минимальную сохранённую ревизию, ответ для устаревшего/некорректного курсора и терминальное состояние недоступного списка. Согласовать состав snapshot с клиентской моделью.

**Уточнение:** сейчас автоматического retention нет, поэтому утверждать, что код уже удаляет нужные события, нельзя. При сохранении всей истории и записи исключительно через `004` сама пагинация `revision > cursor ORDER BY revision LIMIT ...` выглядит корректной.

**M-04. RPC мутации нельзя использовать как непосредственно доступный Siri endpoint с правами только на добавление**

**Тип:** пробел дизайна интеграции.

**Место:** [`SYNC_PROTOCOL_V02.md:32`](https://github.com/MusicMeasurer/shopping-app/blob/6eb6d2ce99e5b5b767d9392fd9e96c717028a09d/cloud/drafts/SYNC_PROTOCOL_V02.md#L32), [`004_apply_item_change.sql:12,41–67,84–85`](https://github.com/MusicMeasurer/shopping-app/blob/6eb6d2ce99e5b5b767d9392fd9e96c717028a09d/cloud/drafts/004_apply_item_change.sql#L41).

**Причина:** функция проверяет UID и доступ к списку, но не scope shortcut credential. Пользовательский JWT позволяет вызывать также `update` и `delete`.

**Сценарий:** Shortcut получает обычный JWT пользователя. Скопировавший его вызывает разрешённые пользователю операции вместо только добавления товара.

**Последствия:** превышение утверждённых полномочий Siri.

**Ожидается:** отдельный отзываемый credential, привязанный к списку и разрешающий только добавление.

**Минимальное безопасное исправление:** отдельный endpoint с проверкой credential, срока действия, отзыва, актуального членства и фиксированного действия `add`. Список определять по разрешённой привязке. Не передавать Shortcut пользовательский JWT с полными правами или `service_role`.

Работающего небезопасного Siri endpoint в проверенных файлах нет; это ограничение будущего использования RPC.

**L-01. Ошибки конфликтов и повторов не имеют устойчивого машинного контракта**

**Тип:** пробел API и обработки ошибок.

**Место:** [`004_apply_item_change.sql:35–39,52–53,79–80`](https://github.com/MusicMeasurer/shopping-app/blob/6eb6d2ce99e5b5b767d9392fd9e96c717028a09d/cloud/drafts/004_apply_item_change.sql#L35).

**Сценарий:** две транзакции одного actor используют один `operation_id` для разных списков. Блокировки списков независимы; обе могут не увидеть запись операции. Одна фиксируется, другая получает `23505` при записи журнала операций.

**Последствия:** клиент может ошибочно считать постоянную ошибку временной и бесконечно повторять запрос. `Version conflict` также не возвращает текущую версию или структурированный конфликт.

**Ожидается:** стабильные различимые ответы: конфликт версии, повтор UUID с другим payload, недоступный объект.

**Минимальное безопасное исправление:** сериализация по ключу actor/operation перед обработкой либо корректная обработка гонки уникальности; стабильные коды ошибок и согласованный conflict payload.

**Важно:** это **не обнаруженная потеря атомарности**. При `23505` изменения проигравшего вызова откатываются. Разные списки означают разные payload, поэтому возвращать им один успешный результат не требуется. Повтор идентичного payload для того же списка уже сериализуется блокировкой списка.

**L-02. `NULL` в `p_action` не отклоняется проверкой действия**

**Тип:** дефект валидации по коду.

**Место:** [`004_apply_item_change.sql:22–24,41–73`](https://github.com/MusicMeasurer/shopping-app/blob/6eb6d2ce99e5b5b767d9392fd9e96c717028a09d/cloud/drafts/004_apply_item_change.sql#L22).

**Причина:** `NULL NOT IN (...)` даёт `NULL`, поэтому `IF` не выбрасывает `Unsupported action`. При подходящих остальных аргументах выполнение проходит в ветку удаления.

**Последствия:** поздняя ошибка вместо корректного отказа валидации. В текущем коде вставка `kind = NULL` в `list_changes.kind NOT NULL` должна откатить вызов целиком; подтверждённого удаления без события здесь нет.

**Ожидается:** немедленный отказ без изменения данных.

**Минимальное безопасное исправление:** явно проверять `p_action IS NULL OR p_action NOT IN (...)`.

**Что новая версия уже обеспечивает по тексту**

Эти меры нельзя продолжать описывать как полностью отсутствующие:

- **Прямые записи товаров:** `003` отзывает у клиентских ролей `INSERT/UPDATE/DELETE/TRUNCATE`.
- **Неизменяемость товара:** новый триггер защищает ID, список и `created_at`.
- **Время товара:** RPC не принимает клиентские timestamps.
- **Версии:** `update/delete` требуют совпадения `p_expected_version`.
- **Повторы:** успешная операция и результат сохраняются в одной транзакции; повтор проверяется до повторного изменения.
- **Удаления:** RPC создаёт мягкое удаление, увеличивает версию и записывает tombstone-событие. Запрет обычного чтения tombstone из `002` этому не противоречит.
- **Порядок изменений:** блокировка строки списка сериализует мутации этого списка; ревизия и событие фиксируются вместе. Это существенно надёжнее временного курсора.
- **Чужие списки:** в последовательных запросах посторонний C должен получать отказ от обеих RPC. Прямого обхода проверки списка по тексту не найдено.
- **Приглашения:** клиентское создание членства закрыто; безопасное принятие приглашений пока отсутствует.
- **Владелец:** прямой перенос владения закрыт. Утверждённая добровольная передача не реализована, включая перевод прежнего владельца в участники, удаление членства нового владельца, аудит и уведомление только новому владельцу.

`md5` здесь используется для сравнения payload, а не для аутентификации. Для строгого требования отклонять любой изменённый payload предпочтительнее хранить канонический payload и сравнивать его непосредственно либо использовать современный хеш. Практическая коллизия для допустимых запросов в рамках этого аудита не установлена.

**Может ли удалённый участник использовать сохранённый JWT?**

**Для нового обычного запроса после зафиксированного удаления членства — по коду не должен.** Проверяется актуальная запись `list_members`, а не список членств внутри JWT. Наличие действительного JWT само по себе членство не восстанавливает.

Исключения и ограничения:

- выполняющийся запрос затронут H-02/H-03;
- длительная транзакция со старым снимком требует отдельной проверки;
- удаление членства не удаляет уже скачанные офлайн-данные;
- отзыв сессии и отзыв членства — разные механизмы: текущие функции не проверяют состояние конкретной Auth-сессии;
- владелец не представлен строкой участника: удалением `list_members` его владение не отзывается.

Следовательно, нельзя утверждать ни «JWT всегда сохраняет доступ после удаления участника», ни «любой отзыв доступа действует мгновенно во всех сценариях».

**Воспроизводимые проверки в изолированной базе — план, не выполненные тесты**

Использовать одноразовую Supabase, три реальных Auth-пользователя A/B/C и anonymous. A — владелец L1/L2, B — участник, C — посторонний. Членство для фикстуры создавать административно: invitation API пока нет.

Сначала применять **неизменённые** `001–005` по порядку с остановкой на первой ошибке и сохранять SQLSTATE. Не добавлять отсутствующие grants незаметно: иначе проверяется другая конфигурация.

Для SQL-тестов в каждой транзакции задавать `SET LOCAL ROLE authenticated` и JWT claims соответствующего пользователя. Для anonymous — роль `anon` без оставшихся claims. Это проверяет SQL/RLS, но **не проверяет подлинность JWT**; её отдельно проверять через Auth/PostgREST.

| Проверка | Действие | Ожидаемый результат |
|---|---|---|
| Миграции | Чистая база, применение `001–005` | Нет ошибок; владельцы и ACL зафиксированы |
| Доступ | A/B/C/anon читают таблицы и вызывают RPC | A/B имеют предусмотренный доступ; C/anon не получают данные |
| Прямой обход | Клиентские записи товаров, журналов, изменение/удаление списка | Отказ, данные неизменны |
| Защита полей | Попытки изменить ID, список, `created_at`, `owner_id` | Отказ |
| Повтор add/update/delete | Один payload и UUID, повтор после commit | Тот же результат; одна новая ревизия и одно событие |
| Изменённый повтор | Тот же UUID, другой payload | Отказ без нового изменения |
| Гонка UUID | Один actor, один UUID, два списка одновременно | Один commit; второй отказ; отсутствие частичных записей |
| Конфликт версии | Два изменения одной версии | Один успех, второй конфликт |
| Tombstone | Удаление и pull с предыдущего курсора | Товар скрыт обычным чтением; tombstone доступен pull |
| Пагинация | Более 500 событий, страницы 1/100/500 | Нет пропусков; курсор равен последней применённой ревизии |
| Входные параметры | NULL, отрицательные/будущие курсоры, размеры 0/501 | Предсказуемый отказ либо явно определённое поведение |
| Начальная ревизия | Создание списка с максимальным `bigint` | После исправления — отказ либо серверная ревизия 0 |
| Удаление аккаунта | Удаление A при общем списке | Общий список сохраняется и передаётся по правилам |
| JWT после исключения | Новый запрос B со старым действительным JWT | Отказ после удаления членства |
| Нулевой actor | Вызов без пользовательского `sub` | Отказ независимо от наличия EXECUTE |

Дополнительно проверить фактические `relowner/proowner`, `relrowsecurity/relforcerowsecurity`, ACL схемы и функций, column grants, default privileges и наследование ролей. Отдельно проверить `TRUNCATE` каждой таблицы с клиентской ролью. Такие проверки выполнять только на одноразовых данных.

Для конкурентных проверок нужны отдельные подключения:

**Сценарий H-02 — мутация и исключение участника**

1. Под B: `BEGIN`, выполнить успешную мутацию, оставить транзакцию открытой.
2. Под A: удалить членство B и попытаться сделать `COMMIT`.
3. Проверить, ожидает ли удаление завершения транзакции B.
4. Завершить B и проверить порядок фиксации и последующие отказы B.

После исправления отзыв должен согласовываться с блокировкой списка. По текущему коду общего механизма блокировки нет.

**Сценарий H-03 — авторизация и снимок pull**

1. Административная тестовая сессия удерживает `ACCESS EXCLUSIVE` на `list_changes`.
2. Новое подключение B впервые вызывает pull; убедиться, что оно ожидает доступ к журналу после проверки членства.
3. Сессия, удерживающая блокировку, удаляет членство B, создаёт новое событие от имени A и фиксирует транзакцию.
4. Проверить, возвращает ли B событие из состояния после отзыва.

Допустимый исправленный результат — отказ либо согласованный снимок до отзыва согласно утверждённому контракту. Смешение старого решения о доступе с новыми данными недопустимо.

Также нужны гонки с `ROLLBACK`, потерей ответа после commit, передачей владельца, удалением аккаунта и различными уровнями изоляции. Пока соответствующие операции не реализованы, часть тестов остаётся критериями приёмки.

**Итоговый вердикт**

- **Готово для test DB: да**, как изолированный прототип для проверки исполнимости, ACL и воспроизведения замечаний. Без production-данных и подключения реальных клиентов.
- **Готово для production: нет.** Не устранены гонки отзыва доступа, разрушительный каскад удаления владельца; не завершены модель привилегий, снимки/retention, передачи владения и интеграционные механизмы.
- **Runtime-безопасность не подтверждена.** Положительные результаты статического анализа не заменяют практические проверки с A/B/C/anon и конкурентными сессиями.
