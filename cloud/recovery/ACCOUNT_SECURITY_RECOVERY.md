# Восстановление данных безопасности аккаунтов

Процедура для базы с 039–044, включая ACL 042. При восстановлении обычного снимка сначала изолируйте целевую базу от клиентов, Auth, Edge Functions и cron. На неё не должно поступать изменений до проверки результата. Секреты подключения берутся из защищённой конфигурации оператора.

## Независимый checkpoint

1. Храните в защищённом хранилище независимо от основных снимков зашифрованные контрольные копии и журнал их покрытия. В копию входят отметки удаления, минимальные доказательства установок удалённых аккаунтов, действующие отпечатки ограничений регистрации и keyring. Коды, письма, адреса и IP в открытом виде в копию не входят. Доступ к расшифровке и доступ к подписи контролируются отдельно. Алиас источника, идентификатор проекта, версия схемы, подтверждённое время покрытия и идентификатор снимка записываются в защищённый журнал. Часы источника и цели должны быть синхронизированы.
2. Для контрольной копии сделайте согласованную паузу записи на источнике, остановите обработчики и дождитесь окончания выполняющихся транзакций. Зафиксируйте время, до которого включительно гарантированно нужны события. Выполните экспорт в одном снимке SQL, сразу шифруя поток. Подпишите зашифрованный файл доверенным ключом и перенесите файл с подписью во внешнее хранилище. Проверьте доступность комплекта и отпечатки ключей. Храните секреты и файлы восстановления вне репозитория, CI-артефактов и диагностических журналов. Для внепланового восстановления необходим проверяемый независимый журнал, покрывающий все подтверждённые операции после снимка, или контрольная копия этой точки с исходной базы при остановленной записи. Один периодический экспорт не подтверждает покрытие между экспортом и остановкой записи.
3. Для примера команды ниже предполагают заранее настроенные сервисы psql, доверенные отпечатки ключей и файлы в защищённом рабочем каталоге. Используйте shell с `pipefail`, ограничьте права каталога и не включайте трассировку команд или запись их входов/выходов.

```bash
set -euo pipefail
umask 077
psql "service=shopping_recovery_source" -X -q -v ON_ERROR_STOP=1 \
  -f cloud/recovery/export_account_security.sql |
  gpg --encrypt --recipient "$RECOVERY_ENCRYPTION_FINGERPRINT" --output account-security.gpg
gpg --local-user "$RECOVERY_SIGNING_FINGERPRINT" --detach-sign \
  --output account-security.sig account-security.gpg
```

## Импорт в закрытую среду

1. По журналу сверьте происхождение, покрытие и отпечаток подписи с доверенным ключом. Проверьте подпись до передачи данных в psql. Для `RECOVERY_REQUIRED_THROUGH` берите независимо подтверждённую границу последней возможной записи с часовым поясом. Если происхождение или непрерывность подтвердить нельзя, оставьте среду закрытой. Сама дата из файла не доказывает непрерывность.
2. Восстановите снимок той же линии базы. Для импорта нужны схемы 039–044 с исходным keyring. Если снимок сделан до создания keyring или он отсутствует, восстановите исходный ключ из подтверждённой защищённой копии до импорта. При несовпадении существующего ключа выясните причину. Скрипт не подменяет его автоматически.
3. Импортируйте только проверенный файл. Скрипт атомарно объединяет отметки, заменяет доказательства удалённых аккаунтов записями из поздней копии, отзывает восстановленные сессии и полностью очищает восстановленные удалённые аккаунты. Он сохраняет исходное время уже завершённого удаления и актуальные счётчики последних 60 минут. Восстановленные коды, запросы, задания и напоминания сбрасываются. Учёт прежних писем из снимка небезопасен, поэтому для существующих аккаунтов нужен свежий запрос. Запуск SMTP и cron оставьте отключённым.
4. До открытия трафика подтвердите отсутствие восстановленных удалённых аккаунтов, активных сессий и старых заданий. Проверьте позднюю очистку зарегистрированной установки, изоляцию другого UUID, отказ для старого кода и сохранение лимита. Подтвердите новый код на контролируемом адресе после согласованного включения обработчика. Профиль, созданный после снимка, требует отдельного восстановления более поздних данных. Процедура сохраняет те независимые профили, которые присутствуют в восстановленной базе.

```bash
gpg --verify account-security.sig account-security.gpg
# Сверить отпечаток подписи и подтверждённую границу по внешнему журналу.
gpg --decrypt account-security.gpg |
  psql "service=shopping_recovery_target" -X -q -v ON_ERROR_STOP=1 \
    -v required_through="$RECOVERY_REQUIRED_THROUGH" \
    -f cloud/recovery/restore_account_security.sql
```

На любой ошибке оставьте среду закрытой. Скрипт допускает повтор с тем же проверенным файлом до открытия трафика. Используйте только непрерывный журнал для данного источника. Хранилище и ключи рабочей среды настраиваются отдельно от репетиции CI.

Для контрольной точки полигона перед 043 используйте тот же экспорт на 042. В нём уже сохраняются отметки, доказательства установок и keyring. Раздел счётчиков пуст, поскольку схема регистрации создаётся в 043. Полный дамп пользовательских данных полигона не требуется по согласованному решению. Импорт контрольной точки в целевую среду выполняется после подготовки схемы до 044 по описанной выше процедуре. Сохранить подписанный шифротекст в защищённом независимом хранилище.
